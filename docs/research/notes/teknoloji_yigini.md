# Architecture & Technology Stack for a Locally Installed Windows M365 Operations-Intelligence App (state: September 2026)

Scope: one or more Windows services on Windows 10/11 or Windows Server, web UI + API over HTTPS on port 6500 (https://localhost:6500, optionally LAN), Microsoft Graph ingestion (mail/SharePoint/OneDrive) with Entra ID sign-in, AI pipeline (LLM extraction, embeddings, agents with human approval; local via Foundry Local/Ollama or cloud), dashboards (projects, phases, tasks, risks, decisions, timelines/event flows, BI). MSI packaging is covered elsewhere; touched here only where it constrains stack choice.

Source-quality legend used below: [primary] = vendor docs / official repo / official blog; [secondary] = credible press (InfoQ, Visual Studio Magazine, heise); [weak] = vendor-marketing or SEO blog, use only as opinion signal.

## 1. Architecture style: modular monolith vs several cooperating Windows services; IPC; module boundaries; audit trail

### Takeaway
For a 2–6 developer team, the most robust shape is a **modular monolith in one .NET Windows service** (Web/API + ingestion + scheduler + workflow/approval + analytics), coordinated through a **durable DB-backed job/outbox table**, plus **at most one optional sidecar process for local LLM inference** (Foundry Local or Ollama) that is reached over **loopback HTTP using the OpenAI-compatible API**. This gives crash isolation where it matters (native model runtimes, GPU/NPU drivers) without distributed-systems overhead. The audit trail should be an append-only, hash-chained provenance log linking evidence → extraction → insight → proposed action → human decision → executed action.

### Cited Findings
- .NET Worker Services run as Windows services via `Microsoft.Extensions.Hosting.WindowsServices` + `builder.Services.AddWindowsService(...)`; Microsoft recommends publishing as a single-file (self-contained) exe for services because it is "less error-prone ... as there aren't any dependent files lying around" — [MS Learn: Create Windows Service using BackgroundService](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service) [primary]
- Since .NET 6 the default `BackgroundServiceExceptionBehavior` is `StopHost`, which stops the host *cleanly*, so the Service Control Manager will **not** restart it; to use SCM recovery options you must terminate with a non-zero exit code (`Environment.Exit(1)`) — same source [primary]. Implication: every extra service multiplies the number of lifecycles to get right.
- SCM recovery is configured per service with `sc.exe failure "<name>" reset= 0 actions= restart/60000/restart/60000/run/1000` — [MS Learn](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service) [primary]
- Foundry Local (GA) runs **in-process**: SDKs are "thin wrappers that call into the Foundry Local Core native library", with an optional web server for REST (OpenAI-compatible chat completions, audio transcription) — [Foundry blog: Foundry Local is GA](https://devblogs.microsoft.com/foundry/foundry-local-ga/) [primary]. Foundry Local 1.1 (May 12, 2026) adds a "built-in web service" that can be started programmatically and used by the OpenAI SDK at a configurable base URL — [Foundry Local 1.1](https://devblogs.microsoft.com/foundry/foundry-local-v1-1/) [primary]
- Ollama on Windows installs per-user without admin into `%LOCALAPPDATA%\Programs\Ollama`, models in `%HOMEPATH%\.ollama`; a standalone `ollama-windows-amd64.zip` exists for "embedding Ollama in existing applications, or running it as a system service via `ollama serve` with tools such as NSSM" — [Ollama docs: Windows](https://docs.ollama.com/windows) [primary]. Default port 11434 — [AlwaysUp: Ollama as a Windows service](https://www.coretechnologies.com/products/AlwaysUp/Apps/OllamaWindowsService.html) [weak]
- Microsoft Graph **webhook** change notifications require "a publicly accessible, HTTPS-secured endpoint"; alternatives are Azure Event Hubs / Event Grid delivery — [MS Learn: Receive change notifications through webhooks](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks), [Change notifications overview](https://learn.microsoft.com/en-us/graph/change-notifications-overview) [primary]. Delta query lets apps "discover newly created, updated, or deleted entities without performing a full read" and "efficiently synchronize changes with a local data store" — [MS Learn: Delta query overview](https://learn.microsoft.com/en-us/graph/delta-query-overview) [primary]
- Delta query is not throttle-exempt; typical incremental cadence 1–15 min, back off on 429, never run two parallel rounds for the same resource — [Nylas: Graph delta query explained](https://cli.nylas.com/guides/graph-api-delta-query-explained) [weak/secondary]
- Outlook per-mailbox Graph limits: 10,000 requests per 10 minutes per app ID + mailbox, 4 concurrent requests, 150 MB upload per 5 minutes; described as fixed limits — [MS Q&A: Graph API rate limits](https://learn.microsoft.com/en-us/answers/questions/5589984/graph-api-rate-limits), [MS Q&A: increasing per-mailbox limits](https://learn.microsoft.com/en-us/answers/questions/5853334/increasing-microsoft-graph-per-mailbox-throttling) [secondary; the current MS Learn throttling page no longer shows an Outlook section when fetched — see Gaps]
- Microsoft Agent Framework (MAF) workflows support human-in-the-loop via `RequestPort` (pauses and waits for external input) and tool approvals — [MS Learn: MAF Workflows HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop), [MS Learn: tool approval](https://learn.microsoft.com/en-us/agent-framework/agents/tools/tool-approval) [primary]
- MAF checkpoints are created at the end of each superstep and capture executor state, pending messages, **pending requests and responses**, and shared state; restoring re-emits pending requests. Checkpoint storage "is a trust boundary ... Never load checkpoints from untrusted or potentially tampered sources" — [MS Learn: MAF Workflows Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints) (updated 2026-09-21) [primary]
- SQL Server 2025 **Ledger** (tamper-evidence) is available in all editions incl. Express; Express also has Database audit, Temporal tables, Change tracking — [MS Learn: SQL Server 2025 editions](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17) [primary]

### Inferences
- **Recommended process topology (default):**
  1. `AppHost` Windows service (one process): Kestrel HTTPS :6500 (UI + REST API + SSE), Graph connectors (delta polling per mailbox/drive), normalization, AI orchestration (LLM calls through `IChatClient`), approval workflow engine, notifications, analytics queries, scheduler.
  2. Optional `AI Runtime` process: Foundry Local's built-in web service or `ollama serve`, bound to 127.0.0.1, managed (started/health-checked/restarted) by AppHost or registered as its own service. Because both expose OpenAI-compatible HTTP, the "IPC" to the model is the same code path as a cloud endpoint (Azure OpenAI / OpenAI / Anthropic via their IChatClient adapters) — only the base URL changes.
  - Split further (separate Ingestion/AI worker services) only when a measured need appears (e.g., memory isolation for large attachment parsing/OCR). Keep module boundaries clean so a split is a deployment change, not a rewrite.
- **IPC options ranked for this case:** (a) shared DB job/outbox table (durable, survives restarts, no extra transport) → first choice for work hand-off between modules/processes; (b) loopback HTTP/gRPC on 127.0.0.1 for request/response to the AI runtime; (c) named pipes only if you need OS-ACL-protected channels between your own processes (not verified in this session: Kestrel named-pipe transport — see Gaps); avoid (d) message brokers (RabbitMQ etc.) — extra Windows service to install/patch.
- **Graph change detection must be pull-based (delta queries)** for a LAN-only install; webhooks need a public HTTPS URL, and Event Hubs/Event Grid need Azure resources — acceptable only for the future Azure/team edition. Design ingestion as: scheduler tick → per-resource delta round (single-flight lock per mailbox/drive) → store raw item + delta token atomically → enqueue normalization job. Budget ≤4 concurrent requests per mailbox.
- **Module boundaries (namespaces/projects inside the monolith, each owning its tables):** `Connectors.Graph` (mail, SharePoint, OneDrive; delta tokens; throttling), `Evidence` (raw item store, blob files, hashes, dedup), `Normalization` (MIME/HTML→text, attachment text extraction, thread reconstruction, chunking), `AI.Extraction` (prompted/structured extraction, embeddings, model registry, prompt versions), `Knowledge` (entities: project/phase/task/risk/decision/person, relations, vector index, FTS), `Workflow.Approval` (proposed actions, human decisions, execution), `Notifications` (in-app SSE, email/Teams via Graph), `Analytics` (read models, aggregates, timelines), `Web/API` (endpoints, auth, static SPA), `Platform` (config, secrets/DPAPI, health, diagnostics, updates). Enforce with architecture tests (not verified tool: e.g., NetArchTest) and "no cross-module table access".
- **Audit/provenance design ("evidence → insight → approved action"):** append-only `audit_event` table (event_id, ts_utc, actor {user oid | service | model}, event_type, subject_type/id, payload JSON, prev_hash, hash = SHA-256(prev_hash‖canonical payload)). Link records: Evidence(graph_id, etag/changeKey, content_sha256, blob_path) → Extraction(model_id, model_version, prompt_version, input evidence ids, output JSON, confidence) → Insight → ProposedAction(target Graph operation, parameters) → Decision(user oid from Entra token, approve/reject/edit, comment) → Execution(Graph request id, response status). If SQL Server 2025 is chosen, Ledger tables give tamper-evidence natively; with SQLite, implement hash chaining + periodic signed digest export. Treat MAF checkpoints as operational state, not the audit record (they are a trust boundary and schema-coupled to executor IDs).

### Gaps
- No authoritative 2026 benchmark comparing one-process vs multi-service .NET Windows apps (memory/startup) was found.
- Kestrel named-pipe transport (`ListenNamedPipe`) and gRPC-over-named-pipes details were not re-verified in this session.

## 2. Backend runtime: .NET vs Node/TypeScript vs Python vs Go/Rust (and ".NET host + embedded Python")

### Takeaway
**.NET 10 LTS (C#, ASP.NET Core Kestrel, Worker Service with `AddWindowsService`)** is the clear fit: first-class Windows service hosting, Event Log integration, single-file self-contained publishing, the most complete Microsoft Graph/MSAL/Agent-Framework/Foundry Local SDK coverage, and the unified `Microsoft.Extensions.AI` abstractions (GA) for swapping local/cloud models. Node SEA is still "Active development" and Python/Go/Rust each add Windows-service or SDK friction. Embed Python only as an isolated child process when a Python-only library is indispensable.

### Inferences
- **Pick .NET 10 (C# 14), x64 + Arm64 builds, self-contained.** Reasons: native SCM integration and Event Log; one runtime for web, workers, Graph, MSAL, MAF, Foundry Local, ONNX; GA provider-neutral AI abstractions; LTS through late 2028 which matches a product lifecycle; plan a .NET 12 LTS (expected Nov 2027, not verified) migration later.
- **Windows 10 caveat:** .NET 10 officially supports only Windows 10 Enterprise LTSC/IoT channels (1607/1809/21H2), not Windows 10 22H2 Pro/Home. Document "Windows 11 23H2+ / Windows Server 2016+ supported; Windows 10 22H2 (ESU) best-effort". This affects all runtimes equally in practice (OS is out of support), but only .NET publishes an explicit matrix.
- **Node/TypeScript** would unify front and back end language, but: SEA is not marked stable, native addons (SQLite drivers, sharp, etc.) need extraction to disk, Windows-service hosting needs a third-party wrapper (node-windows/WinSW/NSSM/Servy), and MAF/Foundry-Local .NET-grade integration is thinner. Viable only for a JS-only team.
- **Python (FastAPI)** has the richest AI/document-parsing ecosystem, but Windows packaging (PyInstaller bundles, AV false positives — not verified), service wrappers of uneven maintenance, GIL/process model and memory footprint make it the riskiest choice for the *host*. Good as an optional worker.
- **Go/Rust:** Go has an official Graph SDK and single static binaries, but no MSAL-grade Entra/WAM story comparable to MSAL.NET, fewer M365/AI enterprise libraries; Rust lacks an official Graph SDK. Not recommended for a small team.
- **".NET host + Python AI worker" pattern:** Pros — access to Python-only libs (docling/unstructured-style document parsing, spaCy, niche embedding models). Cons — two runtimes to patch/sign/ship, larger MSI, extra service lifecycle, IPC contract versioning. If used, run Python as a **child process supervised by the .NET host** (not a separately wrapped NSSM service), talking loopback HTTP/gRPC with a versioned contract, and keep it optional (feature-flagged). Use CSnakes in-process only for small, well-behaved libraries (in-process = no crash isolation).
- **Use Aspire at dev time only** (AppHost orchestrating the service, AI runtime, DB, SPA dev server; dashboard/OTel); do not make the shipped Windows product depend on Aspire runtime components, because of its evergreen (non-LTS) support model.

## 3. HTTPS on port 6500 in a local service (Kestrel vs HTTP.sys, certificates, binding, firewall, HSTS, renewal)

### Takeaway
Use **Kestrel** with a certificate loaded from **LocalMachine\My** (by subject/thumbprint) configured in `Kestrel:Endpoints`, bound to **127.0.0.1:6500 by default** and to the LAN interface only when an admin opts in. Generate a per-machine certificate at install time (SAN: `localhost`, `127.0.0.1`, machine NetBIOS/FQDN) and either trust it locally (self-signed placed in LocalMachine\Root, or a per-install local CA) or, preferably for LAN access, use a certificate from the customer's enterprise PKI. Never ship ASP.NET Core dev-certs or mkcert. Leave HSTS off for loopback (ASP.NET Core already excludes it). HTTP.sys only if Windows Integrated Auth or port sharing is required.

### Cited Findings
- Kestrel endpoint config supports certificate from store: `"Certificate": { "Subject": ..., "Store": ..., "Location": <defaults to CurrentUser>, "AllowInvalid": <defaults false> }`, or from file (`Path`, `KeyPath`, `Password`; PEM+key supported); HTTPS endpoints without a cert fall back to `Certificates:Default` or the dev cert — [MS Learn: Configure endpoints for Kestrel (aspnetcore-10.0)](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0) [primary]
- Kestrel endpoint configuration **reloads by default on configuration change**: unchanged endpoints untouched; removed/modified endpoints get 5 s to drain; "Clients connecting to a modified endpoint might be disconnected or refused while the endpoint is restarted" — same source [primary]
- `serverOptions.Listen(IPAddress.Loopback, port, o => o.UseHttps(...))`, `ListenLocalhost`, `ListenAnyIP`; SNI via `ServerCertificateSelector` or config (`*`, `*.example.org` wildcards) — same source [primary]
- Dev certificate is "available only for the user that generates the certificate"; "Don't create a development certificate in an environment planned for redistribution ... can lead to spoofing and elevation of privilege" — [Kestrel endpoints](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0), [MS Learn: Enforce HTTPS](https://learn.microsoft.com/en-us/aspnet/core/security/enforcing-ssl?view=aspnetcore-10.0) [primary]
- `UseHsts` excludes `localhost`, `127.0.0.1`, `[::1]` by default; HSTS "settings are highly cacheable by browsers" — [MS Learn: Enforce HTTPS](https://learn.microsoft.com/en-us/aspnet/core/security/enforcing-ssl?view=aspnetcore-10.0) [primary]
- **HTTP.sys**: Windows-only; useful for Windows Authentication (Kerberos, kernel mode), port sharing, kernel response caching, direct internet exposure without IIS; HTTPS requires `netsh http add urlacl` and `netsh http add sslcert ipport=... certhash=... appid=...`; admin needed for non-localhost binding; top-level wildcard bindings (`http://*:80/`, `http://+:80`) "should not be used"; HTTP/3 requires `hostnameport` bindings, Windows 11/Server 2022+ — [MS Learn: HTTP.sys (aspnetcore-10.0)](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/httpsys?view=aspnetcore-10.0) [primary]
- **mkcert** creates a local CA in system/Firefox/Chrome/Java trust stores and supports localhost, loopback IPs and LAN hostnames, but is explicitly for development; `rootCA-key.pem` "gives complete power to intercept secure requests" from the machine — [mkcert README](https://github.com/FiloSottile/mkcert) [primary]
- **Entra redirect URI rules** relevant to port 6500 and LAN: `http://` allowed only for localhost; for localhost URIs **the port is ignored** when matching (only for localhost); "Prefer 127.0.0.1 over localhost"; IPv6 loopback `[::1]` unsupported; non-localhost URIs must be `https` and ports are *not* ignored; max 256 redirect URIs for work/school audiences; wildcards discouraged/unsupported for mixed audiences; Blazor Server/ASP.NET Core = "Web" platform, React/Angular/Blazor WASM = "SPA" platform — [MS Learn: Redirect URI best practices](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url) [primary]
- Windows virtual service accounts (`NT SERVICE\<name>`) need no password, can be granted minimal rights, and access the network as the computer account — [MS Learn: Configure Windows service accounts (SQL Server)](https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/configure-windows-service-accounts-and-permissions?view=sql-server-ver17), [MS Learn: Service accounts in Windows Server](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-service-accounts) [primary]

### Inferences
- **Kestrel over HTTP.sys** for this product: cross-platform (keeps the Azure container path open), config-driven certs with hot reload, no `netsh` state to manage/clean up in the MSI. Choose HTTP.sys only if the LAN edition must support Windows Integrated Authentication (Kerberos) instead of Entra sign-in.
- **Certificate strategy (tiered):**
  1. Default (localhost-only): installer (custom action, running as admin) creates an RSA-2048/ECDSA P-256 cert, CN=`<Product> Local`, SAN = `localhost`, `127.0.0.1`, `<hostname>`, `<fqdn>`, 1–2-year validity, stores it in `LocalMachine\My` with the private key ACL granted only to `NT SERVICE\<svc>`; adds the public cert to `LocalMachine\Root` so Edge/Chrome trust it (Firefox may need `security.enterprise_roots.enabled` — not verified). Prefer a **per-install, name-constrained local CA** over a trusted leaf only if you need re-issuance without re-trusting; never keep a CA private key that could sign arbitrary names.
  2. LAN mode: admin imports an enterprise-PKI certificate (or ACME via internal CA) and points `Kestrel:Endpoints:Https:Certificate:Subject/Thumbprint` at it; remote browsers then trust it through domain PKI without touching each client.
- **Binding:** default `Listen(IPAddress.Loopback, 6500)`; LAN mode `ListenAnyIP(6500)` (or the specific NIC) + installer/admin-created Windows Firewall inbound rule restricted to Domain/Private profiles and optionally to local subnet. Keep an `AllowedHosts` list to mitigate DNS rebinding.
- **Entra sign-in implications:** For browser access at `https://localhost:6500`, register `https://localhost/signin-oidc` (port ignored for localhost) or better `https://127.0.0.1/...`; for LAN access each machine hostname+port (`https://pc01.contoso.local:6500/signin-oidc`) must be registered exactly — up to 256 URIs — so the LAN edition needs a customer-owned (single-tenant) app registration or a stable DNS name. This pushes toward a **backend-for-frontend (BFF)** model: ASP.NET Core does OIDC (Web platform), holds tokens server-side (DPAPI-protected cache, machine scope), SPA uses cookies — which also lets background ingestion reuse the delegated refresh token or a separate app-only credential (certificate in LocalMachine store) for org-wide ingestion.
- **Renewal:** a hosted `CertificateMaintenanceService` checks expiry daily; ≥30 days before expiry it issues a new cert, updates the configured subject/thumbprint in `%ProgramData%\...\appsettings.Local.json`; Kestrel's default config reload swaps the endpoint (brief connection drop, per docs). Store-only changes without a config change do not trigger reload (inference — verify).
- **HSTS:** do not emit HSTS for localhost (default exclusion); for a LAN FQDN with enterprise PKI, a short max-age HSTS is acceptable; never `includeSubDomains` on a corporate parent domain from a desktop product.

### Gaps
- Exact Chrome/Edge/Firefox 2026 behavior for self-signed certs trusted via LocalMachine\Root vs private network access (PNA) prompts for LAN IPs was not researched.
- Whether Kestrel reloads a store-based certificate when only the store content changes (same subject) was not verified.

## 4. Frontend: SPA vs Next.js vs Blazor; component library; visualization libraries; real-time updates

### Takeaway
Ship a **React + TypeScript + Vite SPA served as static files by Kestrel** (no Node runtime on the target machine), using **Fluent UI React v9** for the Microsoft 365 look, **Apache ECharts** for BI charts, **React Flow (@xyflow/react, MIT)** for event-flow/relationship graphs, **vis-timeline** for project/phase timelines, **AG Grid Community (MIT)** for large tables, and **.NET 10 native Server-Sent Events** for push updates (SignalR only if bidirectional real-time is needed). ## 5. Local background processing: queues, schedulers, durable workflows; retries/idempotency

### Takeaway
Keep it in-process and DB-backed: **`System.Threading.Channels` for in-memory fan-out**, a **durable job/outbox table in the app DB** for anything that must survive restarts, **Quartz.NET (or TickerQ) for cron-like schedules**, and **Microsoft Agent Framework workflows (with a custom DB-backed checkpoint store) for agentic multi-step flows with human approval**. Model the business approval flow (proposed action → decision → execution) as an explicit persisted state machine, not inside an external orchestrator. Avoid Temporal/Dapr (extra server runtimes); consider Durable Task Framework with the SQL Server provider only if SQL Server is chosen.

### Cited Findings
- **Hangfire**: fire-and-forget/delayed/recurring jobs with dashboard; core LGPL, Pro (batches, Redis) commercial. **Quartz.NET**: most mature scheduler — calendars, misfire policies, priorities, DB clustering; no dashboard; permissive license. **TickerQ**: source-generated, EF Core persistence, dashboard, in-memory timers instead of DB polling, but young ("how does this behave in year three" unknown) — [SteadyCron: Hangfire vs Quartz vs TickerQ](https://steadycron.com/blog/dotnet-job-schedulers-compared/), [SteadyCron: TickerQ vs Hangfire](https://steadycron.com/blog/tickerq-vs-hangfire/) [weak/secondary]
- TickerQ: MIT/Apache-2.0 dual license; EF Core providers for PostgreSQL, SQL Server, **SQLite**, MySQL; Redis option; SignalR dashboard; retries with backoff; "zero reflection, AOT ready"; ~3.6k GitHub stars — [TickerQ GitHub](https://github.com/Arcenox-co/TickerQ) [primary]
- Quartz.NET AdoJobStore includes a `SQLite-Microsoft` provider (Microsoft.Data.Sqlite) — [quartznet dbproviders.properties](https://github.com/quartznet/quartznet/blob/main/src/Quartz/Impl/AdoJobStore/Common/dbproviders.properties), [Quartz.NET Job Stores](https://www.quartz-scheduler.net/documentation/quartz-3.x/tutorial/job-stores.html) [primary]
- **Durable Task Framework** (DTFx) — [Azure/durabletask](https://github.com/Azure/durabletask) [primary]; **MSSQL provider** stores orchestration state in SQL Server/Azure SQL, supports local offline dev on SQL Server Express — [durabletask-mssql docs](https://microsoft.github.io/durabletask-mssql/), [MS Learn quickstart](https://learn.microsoft.com/en-us/azure/azure-functions/durable/quickstart-mssql) [primary]; `durabletask-go` has a SQLite backend — [microsoft/durabletask-go](https://github.com/microsoft/durabletask-go) [primary]
- **Temporal** dev server: single process, SQLite persistence via `--db-filename`, runs on Windows, but "not intended for production use" — [Temporal docs: Run a development server](https://docs.temporal.io/develop/run-a-development-server) [primary]
- 2026 trend: "SQLite is all you need for durable workflows" (Obelisk post, HN) — [byteiota](https://byteiota.com/sqlite-durable-workflows-skip-temporal/), [TechPlanet](https://techplanet.today/post/sqlite-is-all-you-need-for-durable-workflows-a-practical-guide-to-lightweight-orchestration) [weak]
- MAF workflows: checkpoints per superstep; HITL via `RequestPort`; resume/rehydrate requires identical topology and stable executor/agent IDs (`ChatClientAgentOptions.Id`); C# docs show `CheckpointManager.CreateInMemory()`; Python ships In-Memory, File, Cosmos storages — [MS Learn: MAF Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints), [MS Learn: HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop) [primary]

### Inferences
- **Recommended mechanics:**
  - `jobs` table (id, type, payload JSON, idempotency_key UNIQUE, status, attempts, next_run_at, locked_by, locked_until, last_error) polled by a `JobDispatcher` BackgroundService (single process ⇒ simple `UPDATE ... WHERE status='ready' ... RETURNING` claim), with exponential backoff + jitter and a dead-letter state surfaced in the UI. Channels only as the in-memory buffer between dispatcher and N workers (bounded, per job type concurrency: e.g., Graph per-mailbox ≤4, LLM ≤ GPU capacity).
  - **Transactional outbox**: every state change that triggers work writes the job row in the same transaction ⇒ exactly-once *intent*, at-least-once *execution*; handlers must be idempotent (keys: Graph item id + changeKey for ingestion; content hash + model/prompt version for extraction; action id for executions).
  - **Schedules:** Quartz.NET with SQLite/SQL Server store if you need calendars/misfire semantics; otherwise TickerQ (lighter, EF Core) or a minimal cron table. Hangfire is fine functionally but its first-party storages are SQL Server/Redis (SQLite storage is community — not verified) and LGPL/Pro licensing is a procurement question.
  - **Approval flow:** explicit state machine (`Proposed → PendingApproval → Approved|Rejected|Edited → Executing → Done|Failed`) in the DB with audit events; the UI queries pending items; approval triggers an execution job. MAF `RequestPort` is used *inside* an agent run to ask for info/approval, but persist the pending request in your own tables as the source of truth, because MAF checkpoints are schema/ID-coupled and a trust boundary.
- **Why not Temporal/Dapr/Elsa for v1:** each adds a server/sidecar or a large framework to install, patch and back up on every customer PC; Temporal's dev server is explicitly not production. Durable Task + MSSQL is a reasonable upgrade path if/when the team edition runs on SQL Server/Azure SQL.

### Gaps
- Elsa Workflows 3 and Dapr Workflow were not researched in this session (no sources fetched).
- No verified .NET SQLite backend for DTFx found; Hangfire SQLite storage maturity not verified.

## 6. Local data layer: SQLite vs PostgreSQL vs SQL Server 2025 Express/LocalDB vs others; vectors; graph; blobs; analytics; backup; sizing

### Takeaway
For the single-PC product, **embedded SQLite (WAL) + FTS5 + a vector index (sqlite-vec brute-force now; SQLite's official Vec1 or sqlite-vec ANN when stable) + raw emails/attachments as content-addressed files on disk** is the lowest-friction, most robust choice. **SQL Server 2025 Express** is the strongest *server-grade* alternative on Windows (native VECTOR type in all editions, full-text search now included, graph tables, Ledger) but has a **50 GB DB cap, 1,410 MB buffer pool, 4 cores**, and its DiskANN vector index is still **preview**. PostgreSQL + pgvector on Windows requires building pgvector from source — poor fit for a shipped product. Keep EF Core and a storage abstraction so the team/Azure edition can use SQL Server 2025/Azure SQL.

### Cited Findings
- **SQL Server 2025 Express** scale limits: lesser of 1 socket/4 cores; 1,410 MB buffer pool; **50 GB max DB size**; Express "includes all the functionality that was available in SQL Server Express edition with Advanced Services" (incl. Full-Text Search); LocalDB is an Express option; no SQL Server Agent, no backup encryption/compression, no TDE in Express; Ledger, Always Encrypted, graph tables, temporal tables, JSON type/index, change tracking all in Express — [MS Learn: SQL Server 2025 editions](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17) [primary]
- SQL Server 2025 AI features in **all editions incl. Express**: native vector type (GA), DiskANN vector indexing (**requires PREVIEW_FEATURES**), local ONNX models (preview), embedding generation, chunking — same source [primary]. `VECTOR_SEARCH`, `CREATE VECTOR INDEX`, float16 vectors, `AI_GENERATE_EMBEDDINGS` are preview features — [MS Learn: VECTOR_SEARCH](https://learn.microsoft.com/en-us/sql/t-sql/functions/vector-search-transact-sql?view=sql-server-ver17), [SQLServerCentral](https://www.sqlservercentral.com/articles/vector-search-in-sql-server-2025-storing-embeddings-querying-them-and-what-to-watch-out-for) [primary/secondary]. **Conflict:** a third-party article states DiskANN indexes are limited to Standard/Enterprise — [search summary citing dbvis/aleson](https://www.dbvis.com/thetable/sql-server-vector-data-type-search-and-indexing/) [weak]; the official editions table says Express = Yes (preview). Prefer the official table.
- **LocalDB** runs in user mode under the owning user's security context; files in user's AppData; "An instance of LocalDB owned by the built-in accounts such as NT AUTHORITY\SYSTEM can have manageability issues due to Windows file system redirection" — [MS Learn: SQL Server Express LocalDB](https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/sql-server-express-localdb?view=sql-server-ver17) [primary]
- **SQLite FTS5** full-text virtual tables — [sqlite.org/fts5](https://sqlite.org/fts5.html) [primary]
- **sqlite-vec**: "pre-v1, so expect breaking changes"; float/int8/binary vectors in `vec0` virtual tables with metadata/auxiliary columns; pure C, runs on Windows; bindings for Python/Node/Ruby/Go/Rust (no .NET package listed); sponsored by Mozilla Builders et al. — [asg017/sqlite-vec](https://github.com/asg017/sqlite-vec) [primary]. Latest stable v0.1.9; ANN (rescore, IVF, DiskANN) only in **v0.1.10-alpha** as of mid-2026 — [sqlite-vec releases](https://github.com/asg017/sqlite-vec/releases), [ANN tracking issue #25](https://github.com/asg017/sqlite-vec/issues/25) [primary], [third-party tracker](https://github.com/jannekbuengener/sample-brain/issues/74) [weak]. Community fork exists adding pagination/optimize — [photostructure/sqlite-vec](https://github.com/photostructure/sqlite-vec) [primary]
- **SQLite Vec1** (official SQLite-team ANN vector extension) is under development, "no vec1 release" yet, feature-complete for 1.0 but testing/optimization pending — [SQLite forum: Vec1 update](https://sqlite.org/forum/info/c9d69d74c6644dd19614851e46e2bd29615b922407fdb730529a755e2630d652), [SQLite forum: Vec1 announcement](https://sqlite.org/forum/info/ae5edea02aad9b7d5f38f24e77c4c4c57d36fe4b4a52a44bdcc5e13c7d133710), [sqlite.org/vec1](https://sqlite.org/vec1) [primary]
- **SQLite encryption in .NET**: Microsoft.Data.Sqlite supports encryption only via an encryption-enabled native library — [MS Learn: Microsoft.Data.Sqlite encryption](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/encryption) [primary]; `SQLitePCLRaw.bundle_e_sqlcipher` is deprecated (last 2.1.11, Mar 2025) and SQLitePCLRaw 3.0 stopped shipping free encryption builds; options: Zetetic SQLCipher (commercial/community), SQLite3 Multiple Ciphers bundle (MIT) — [NuGet bundle_e_sqlcipher](https://www.nuget.org/packages/SQLitePCLRaw.bundle_e_sqlcipher), [SQLitePCL.raw wiki: encryption options](https://github.com/ericsink/SQLitePCL.raw/wiki/SQLite-encryption-options-for-use-with-SQLitePCLRaw), [Zetetic SQLCipher for .NET](https://www.zetetic.net/sqlcipher/sqlcipher-for-dotnet/) [primary]; SQLite3MC bundle 2.4.0 (July 2026) claim from [botnexus issue #4114](https://github.com/sytone/botnexus/issues/4114) [weak]
- **pgvector on Windows**: build with Visual Studio C++ tools, `nmake /F Makefile.win` in the x64 Native Tools prompt against `C:\Program Files\PostgreSQL\18` — [pgvector README](https://github.com/pgvector/pgvector) [primary]; EDB's PostgreSQL 18 Windows StackBuilder lacked PostGIS/LanguagePack at time of issue — [edb-installers #415](https://github.com/EnterpriseDB/edb-installers/issues/415) [primary]
- **Vector connectors for .NET**: `Microsoft.Extensions.VectorData.Abstractions` GA, but implementations remain preview: `Microsoft.SemanticKernel.Connectors.SqliteVec` 1.74.0-preview (Mar 2026), `...Connectors.SqlServer` 1.70.0-preview (Jan 2026), Postgres connector preview — [NuGet SqliteVec](https://www.nuget.org/packages/Microsoft.SemanticKernel.Connectors.SqliteVec/), [NuGet SqlServer](https://www.nuget.org/packages/Microsoft.SemanticKernel.Connectors.SqlServer), [MS Learn: Postgres connector (Preview)](https://learn.microsoft.com/en-us/semantic-kernel/concepts/vector-store-connectors/out-of-the-box-connectors/postgres-connector), [MS Learn: SQL Server connector (Preview)](https://learn.microsoft.com/en-us/semantic-kernel/concepts/vector-store-connectors/out-of-the-box-connectors/sql-connector) [primary]
- **DuckDB 1.4 LTS**: AES-256 database encryption, MERGE INTO, Iceberg writes; 1.4.x are bugfix/security LTS releases; MIT; EF Core 10 provider reported — [LinuxToday](https://www.linuxtoday.com/blog/duckdb-1-4-lts-released-with-database-encryption-merge-and-iceberg-writes/) [secondary], [Medium: DuckDB for .NET with EF Core](https://medium.com/@Skuirrel/duckdb-for-net-columnar-analytics-using-ef-core-0153b8fbf633) [weak]
- **Email size signals**: modern Exchange Online messages are ~60× the 2–4 KB messages of 1996 (≈120–240 KB/item); M365 notification emails 174–472 KB — [Office 365 for IT Pros](https://office365itpros.com/2021/05/06/exchange-mailbox-item-size/) [secondary]. Typical business mailbox growth 3–8 GB/year (light 1–3, heavy 10–25) — [Cyfuture KB](https://cyfuture.cloud/kb/storage/what-is-the-preferred-mailbox-storage-size-per-user-in-gb) [weak]
- Foundry Local embedding model `qwen3-embedding-0.6b` with configurable dimensions — [Foundry Local 1.1](https://devblogs.microsoft.com/foundry/foundry-local-v1-1/) [primary]

### Inferences
- **Recommended layout (local edition):**
  - `%ProgramData%\<Vendor>\<Product>\data\app.db` — SQLite, WAL mode, `synchronous=NORMAL`, single writer queue in-process; EF Core for OLTP entities; raw SQL for FTS5/vector queries.
  - `...\blobs\sha256\ab\cd\<hash>` — raw `.eml`/MIME and attachments, content-addressed (dedups identical attachments across threads), optionally NTFS-compressed; DB stores metadata, extracted text, chunks, embeddings, provenance. Keeps DB small and backups incremental.
  - Vectors: at local scale brute-force is adequate: e.g., 200k emails × ~3 chunks = 600k vectors × 1024 dims × 4 B ≈ 2.4 GB float32 (≈0.6 GB int8, ≈75 MB binary) — scan time acceptable with int8/binary pre-filter + float rescoring. Hide behind `IVectorIndex` so sqlite-vec (pre-v1), Vec1 (unreleased), or an in-process .NET index can be swapped.
  - Graph modeling: relational edge table (`relation(src_type, src_id, rel_type, dst_type, dst_id, evidence_id, confidence)`) + recursive CTEs; no separate graph DB needed at this scale. (SQL Server graph tables are an option if SQL Server is chosen.)
  - Analytics: SQL views/materialized summary tables refreshed by jobs; add DuckDB only if ad-hoc BI over millions of rows becomes slow (DuckDB can read SQLite/Parquet — not re-verified).
- **Sizing (inference):** for 10 mailboxes × 5 GB/yr ≈ 50 GB/yr raw blobs on disk, while the DB (text + metadata + chunks + int8 embeddings) is typically ~10–20% of raw size ⇒ a few GB/yr. This fits SQLite easily; it would also fit SQL Server Express's 50 GB cap *only if blobs stay on disk*, and the 1.4 GB buffer pool would limit vector/full-text query speed as data grows.
- **Encryption at rest:** simplest robust option is **BitLocker + NTFS ACLs (service SID only) + DPAPI-protected secrets**; add SQLCipher/SQLite3MC only if customers require DB-file encryption independent of the OS (note packaging/licensing churn above). SQL Server Express lacks TDE.
- **Backup/restore:** SQLite Online Backup API / `VACUUM INTO` to `backup\app-YYYYMMDD.db` + blob folder snapshot (VSS or robocopy of immutable content-addressed files); restore = stop service, replace, start. SQL Server Express: `BACKUP DATABASE` works but no Agent — schedule from the app's scheduler.
- **Why not SQL Server Express as default:** separate installer (~ admin, reboot risk, patching via Microsoft Update), 50 GB/1.4 GB limits, vector index preview; **why it stays attractive:** same engine as Azure SQL for the team edition, Ledger for audit, full-text search, vectors — make it the *supported alternative* for Windows Server deployments that already run SQL Server.
- **Why not PostgreSQL on Windows:** extra service, pgvector compilation per PG major version, fewer Windows-native ops tools; good for a Linux/Azure team edition (Azure Database for PostgreSQL has pgvector — not verified here).
- LiteDB/RavenDB/LanceDB: not recommended for the system of record (smaller .NET ecosystems / no FTS+vector+relational combo verified in this session).

### Gaps
- No official .NET NuGet for sqlite-vec was found; loading requires shipping the native `vec0.dll` and `SqliteConnection.LoadExtension` (not verified end-to-end on .NET 10).
- EF Core 10 support for SQL Server 2025 `vector` type and `VECTOR_SEARCH` not verified in this session.
- Reliable, primary statistics for average enterprise mailbox growth were not found (only a vendor KB).
- LanceDB/.NET and RavenDB vector features not researched.

## 7. Local observability: logging/tracing, Event Log, health, diagnostics bundle, crash recovery

### Takeaway
Instrument with **OpenTelemetry (traces/metrics) + structured logging (Microsoft.Extensions.Logging, optionally Serilog)** writing **rolling JSON files under %ProgramData%** and **Warning+ to the Windows Event Log**, expose **/health/live and /health/ready**, provide a one-click **diagnostics bundle**, and rely on **SCM recovery actions + `Environment.Exit(1)` on fatal errors** for crash recovery. OTLP export to a collector is optional (enterprise customers, team edition).

- .NET Windows service template uses `EventLogLoggerProvider`; default Event Log severity Warning; configure `Logging:EventLog:SourceName/LogName/LogLevel` — [MS Learn: Windows service](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service) [primary]

- Serilog → OTel via `Serilog.Sinks.OpenTelemetry` (OTLP gRPC/HTTP); default OTLP endpoint localhost:4317 — [SigNoz](https://signoz.io/blog/opentelemetry-serilog/), [Dash0 guide](https://www.dash0.com/guides/opentelemetry-logging-dotnet-serilog) [secondary]; OTLP exporter for .NET — [open-telemetry/opentelemetry-dotnet OTLP README](https://github.com/open-telemetry/opentelemetry-dotnet/blob/main/src/OpenTelemetry.Exporter.OpenTelemetryProtocol/README.md) [primary]
- Aspire dashboard/OTel is part of the Aspire dev experience — [aspire.dev: What's new in 13](https://aspire.dev/whats-new/aspire-13/) [primary]

### Inferences
- **Logs:** `%ProgramData%\<Vendor>\<Product>\logs\app-.json` (daily roll, size cap, 14–30 days retention); PII-scrubbing enricher (email addresses/subjects hashed unless "verbose diagnostics" is enabled by an admin); correlation ids = OTel TraceId; AI calls logged with model id, prompt version, token counts, latency (content only in opt-in debug).
- **Metrics:** OTel meters (ingestion lag per mailbox, delta round duration, 429 count, queue depth, LLM tokens/s, GPU/NPU availability); shown on an internal admin page; OTLP export optional.
- **Health:** `/health/live` (process), `/health/ready` (DB writable, disk space, cert validity > N days, Graph token valid, AI runtime reachable) — used by the UI banner and by an optional Windows Scheduled Task/monitoring.
- **Diagnostics bundle:** admin-only endpoint/CLI (`<product>.exe diag --out bundle.zip`) collecting last N log files, redacted config, versions (OS, .NET, model runtime), health output, DB integrity check result, event log excerpts; optional `dotnet-dump`-style minidump on crash via Windows Error Reporting LocalDumps registry (not verified here).
- **Crash recovery:** SCM recovery (restart after 60 s, twice, then run a notifier), reset period 1 day; idempotent jobs + outbox ensure restart safety; "delayed auto-start" so the service starts after network is up.

## 8. Auto-update, configuration management, per-machine vs multi-user

### Takeaway
Treat updates as **MSI major upgrades** distributed via Intune/winget/ConfigMgr (enterprise-friendly, auditable), with an optional in-app "update available" notifier that downloads and launches the signed MSI; avoid desktop-oriented self-updaters (Velopack) which have historically not supported Windows services. Install **per-machine**, one service instance, with **Entra-authenticated multi-user access through the web UI** (roles in-app), not per-Windows-user instances. Config = immutable `appsettings.json` in the install dir + admin overrides in `%ProgramData%` + DPAPI-protected secrets.

### Cited Findings
- Velopack "does not support installing or updating Windows Services" (statement dated July 2024; may be outdated) — [Velopack docs discussion](https://github.com/velopack/velopack.docs/discussions/13), [Velopack GitHub](https://github.com/velopack/velopack) [primary, possibly outdated]

- Kestrel endpoint config (incl. certificates) reloads on configuration change by default — [MS Learn: Kestrel endpoints](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0) [primary]
- MSAL token cache persistence uses DPAPI on Windows — [MSAL extensions wiki](https://github.com/AzureAD/microsoft-authentication-extensions-for-dotnet/wiki/Cross-platform-Token-Cache) [primary]
- LocalDB is per-user and problematic under SYSTEM — [MS Learn: LocalDB](https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/sql-server-express-localdb?view=sql-server-ver17) [primary]
- Virtual service accounts `NT SERVICE\<name>` — [MS Learn](https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/configure-windows-service-accounts-and-permissions?view=sql-server-ver17) [primary]
- Ollama default install is per-user (no admin, `%LOCALAPPDATA%`) — [Ollama docs](https://docs.ollama.com/windows) [primary]; Foundry Local can be bundled inside the app installer — [Foundry Local GA](https://devblogs.microsoft.com/foundry/foundry-local-ga/) [primary]

### Inferences
- **Stack consequences of MSI-based updates:** self-contained .NET publish (no shared runtime dependency to service); DB migrations run by the service on startup behind a version gate with automatic pre-migration backup; schema changes must be forward-only and resumable; keep blob format stable.
- **Config precedence:** `install\appsettings.json` (defaults, replaced on upgrade) → `%ProgramData%\...\appsettings.Local.json` (admin-edited, preserved) → environment variables → optional HKLM policy keys (for Intune/GPO-managed settings like "LAN access allowed", "cloud LLM allowed"). Secrets (client cert thumbprint, cloud API keys, DB encryption key) protected with DPAPI **LocalMachine scope** + ACL to the service SID, or stored in the cert store.
- **Per-machine install, multi-user via Entra:** the service runs as `NT SERVICE\<Product>`; users on the same PC or LAN authenticate with Entra in the browser; authorization by Entra app roles/groups; no per-Windows-user data silos. Avoid LocalDB and per-user Ollama installs for the same reason (they bind to a user profile); ship the model runtime per-machine (Foundry Local bundled, or Ollama standalone zip under Program Files with models in ProgramData).

### Gaps
- Current (2026) Velopack service support not re-verified; winget/Intune specifics belong to the packaging research.

## 9. Optional future hybrid: same codebase on Azure (Container Apps) for a team/server edition

### Takeaway
Portability is mostly a matter of **abstractions at five seams** — hosting, storage, queue, AI provider, change-detection — all of which .NET already provides: the same ASP.NET Core app runs as a Windows service (`AddWindowsService`) or in a Linux container; `IChatClient`/`IEmbeddingGenerator` swap local ↔ Azure OpenAI/Foundry; EF Core swaps SQLite ↔ SQL Server/Azure SQL; blob/queue interfaces swap disk/DB-table ↔ Azure Blob/Service Bus; Graph delta polling ↔ webhooks/Event Hubs. Use Aspire for local orchestration and ACA deployment tooling.

### Inferences
- **Seams to design on day 1:** `IHostingProfile` (WindowsService vs Container — `AddWindowsService` is harmless when not running under SCM; verify), `IBlobStore` (disk ↔ Azure Blob), `IJobQueue` (DB table ↔ Azure Service Bus/Storage Queue), `IVectorIndex` (sqlite-vec/in-proc ↔ Azure SQL vector / Azure AI Search), `IChangeFeed` (delta polling ↔ Graph notifications via Event Hubs), `ICertificateProvider` (LocalMachine store ↔ ACA managed certs), `ISecretStore` (DPAPI ↔ Key Vault), auth (single-tenant local registration ↔ multi-tenant SaaS registration).

- **Avoid lock-in to local-only primitives:** no reliance on named pipes for core flows, no Windows-only APIs outside the `Platform.Windows` module (Event Log, DPAPI, cert store, SCM), target `net10.0` for core libraries and `net10.0-windows` only for the host shim.

## 10. Synthesis: the ONE recommended stack for the local-Windows scenario (with justification)

### Takeaway
**.NET 10 LTS modular monolith as a single Windows service (Kestrel HTTPS :6500, cert from LocalMachine store) + React/Vite/TypeScript SPA with Fluent UI v9 served statically + SQLite (WAL, FTS5, vector index behind an abstraction) with content-addressed blob files on disk + DB-backed job/outbox queue with Quartz.NET/TickerQ schedules + Microsoft.Extensions.AI / Microsoft Agent Framework 1.x for LLM extraction and HITL agents, with Foundry Local (bundled, WinML-accelerated) as default local runtime and Azure OpenAI/other cloud models as configurable providers + Microsoft Graph .NET SDK with delta-query polling + MSAL.NET (BFF, DPAPI token cache) + OpenTelemetry/structured file logs + Event Log.** SQL Server 2025 is the supported alternative DB for server installs and the bridge to Azure SQL.

| Concern | Recommended | Runner-up | Rejected (why) |
|---|---|---|---|
